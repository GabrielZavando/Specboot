# `.specboot.example.json` — Comentario por campo

JSON no permite comentarios, así que este README documenta cada campo del ejemplo
canónico en `.specboot.example.json`. El esquema completo y su validación viven en
[`docs/specboot-json-standard.md`](docs/specboot-json-standard.md).

## Campos

- **`frameworkVersion`** (requerido, string SemVer): versión del framework que el
  proyecto requiere. Debe compararse con la versión instalada de
  `@gabrielzavando/specboot` (ver TICKET-0.4 para saltos de versión). Ejemplo: `"0.1.1"`.

- **`name`** (opcional, string): nombre legible del proyecto. Solo metadato.

- **`description`** (opcional, string): descripción libre del proyecto. Solo metadato.

- **`services`** (requerido, array de strings): rutas relativas (desde la raíz) a las
  carpetas con código del proyecto. `"."` denota la raíz misma (mono-repo sin
  subcarpetas). Cada entrada debe existir. El Makefile de Fase 5 las usa para saber
  qué lintear. Ejemplo: `["backend", "frontend"]`.

- **`stack`** (requerido, string o array de strings): stack(s) del proyecto, determina
  qué linters aplican (`node`, `python`, `framework`, etc.). Ejemplo: `["node", "python"]`.

- **`extraStandards`** (opcional, array de strings): rutas de `docs/` adicionales que
  el agente debe cargar según la tarea. Deben vivir bajo `docs/`. Ejemplo:
  `["docs/client-rules.md"]`.

- **`layers`** (opcional, object): mapa servicio → array de etiquetas de capa. Metadato
  opt-in de nomenclatura usado por el skill `plan-change` (Step 5) para etiquetar capas
  y `Suggested Path`/`Test Path`. Si se omite, `plan-change` usa las capas por defecto
  según `stack`. El validador solo exige que, de estar presente, sea un objeto.
  Ejemplo: `{ "backend": ["domain","application","infrastructure"], "frontend": ["smart","dumb"] }`.

## Casos mínimos

Mono-repo con un servicio en la raíz (el propio Specboot):
```json
{ "frameworkVersion": "0.1.1", "services": ["."], "stack": "framework" }
```
