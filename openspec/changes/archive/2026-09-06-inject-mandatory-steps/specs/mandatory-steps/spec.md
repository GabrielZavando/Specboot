# mandatory-steps Specification

## ADDED Requirements

### Requirement: The framework MUST provide a mandatory-steps document with three phases
The framework SHALL provide `docs/openspec-tasks-mandatory-steps.md` as the single source of truth for the mandatory implementation checklist, defining three phases: pre-implementation (active branch follows the applicable convention, clean git state), during (module unit tests; the new test fails before implementing — RED), and post (run `verify`; run `adversarial-review`).

#### Scenario: Document defines pre, during and post phases
- **GIVEN** the framework repository
- **WHEN** an agent or developer reads `docs/openspec-tasks-mandatory-steps.md`
- **THEN** the document exists and defines the pre-implementation phase (branch convention and clean git state)
- **AND** it defines the during phase (module unit tests; the new test fails before implementing)
- **AND** it defines the post phase (run `verify`, run `adversarial-review`)

### Requirement: plan-change MUST inject the mandatory steps into every generated tasks.md
The `plan-change` skill SHALL inject a `## Mandatory Steps` section into every generated `tasks.md`, copying its content from the mandatory-steps document read at generation time. The skill SHALL NOT contain a hardcoded copy of the steps.

#### Scenario: Generated tasks.md carries the mandatory steps
- **GIVEN** a change generated by `/plan-change`
- **WHEN** the `tasks.md` artifact is written
- **THEN** it contains a `## Mandatory Steps` section sourced from the document read at generation time
- **AND** the skill contains no hardcoded copy of the steps

### Requirement: plan-change validation MUST check the injected section
The Step 6 validation checklist of `plan-change` SHALL include the check that `tasks.md` includes the `## Mandatory Steps` section, and the flow SHALL NOT report success when that check fails.

#### Scenario: Validation fails without the section
- **GIVEN** a generated `tasks.md` without the `## Mandatory Steps` section
- **WHEN** the Step 6 checklist runs
- **THEN** the generation is not reported as successful
- **AND** the failing artifact is regenerated before reporting

### Requirement: The AGENTS bridge MUST reference the mandatory-steps document
The dynamic-loading section (§2) of `AGENTS.md` SHALL reference `docs/openspec-tasks-mandatory-steps.md` as framework content injected by `plan-change` into every generated `tasks.md`.

#### Scenario: Bridge surfaces the document
- **GIVEN** the `AGENTS.md` bridge
- **WHEN** an agent resolves dynamic context for an implementation task
- **THEN** §2 references the mandatory-steps document and its injection mechanism

### Requirement: The document MUST be distributed as a framework file
`docs/openspec-tasks-mandatory-steps.md` SHALL be listed in `FRAMEWORK_ITEMS` (`specboot.sh`) and in the `files` allowlist of `package.json`; `docs/docs-standard.md` SHALL list it in the canonical tree and `docs/framework-contract.md` SHALL include it in the `docs/` skeleton created by `init`. It SHALL NOT be added to `REQUIRED_FILES` of `specboot.sh`.

#### Scenario: Consumer receives the document via init/update
- **GIVEN** a consumer project running `specboot init` or `specboot update` with framework version 0.6.0
- **WHEN** the framework copies the injected files
- **THEN** `docs/openspec-tasks-mandatory-steps.md` exists in the consumer project
- **AND** the npm distribution includes it via the `files` allowlist

#### Scenario: Skipping a minor update does not break --ci
- **GIVEN** a consumer project that has not run `specboot update` for version 0.6.0
- **WHEN** `specboot.sh --ci` validates the project
- **THEN** the missing mandatory-steps document does not raise a validation error (it is not in `REQUIRED_FILES`)

### Requirement: The improvement plan MUST record completion and follow-up tickets
`PLAN_MEJORAS_SPECBOOT.md` SHALL mark M-601 as completed, SHALL add history row v3.6, and SHALL register a new section "Fase 10 — Follow-ups de auditoría (patrón M-403)" listing pending tickets M-904 (W1 staleness semantics), M-905 (W2 `Gate-Bypass` trailer vocabulary), M-906 (W3 reconcile M-901 SemVer) and M-907 (W4 residual phrase in archived spec). M-403 SHALL remain visible as pending in its Phase 4 section.

#### Scenario: Follow-ups registered without implementation
- **GIVEN** the four adversarial warnings (W1–W4) from change `enforce-commit-gates`
- **WHEN** `inject-mandatory-steps` completes
- **THEN** the plan shows M-601 marked completed with history row v3.6
- **AND** Phase 10 lists M-904..M-907 as pending tickets with problem and proposal descriptions
- **AND** M-403 remains pending in its Phase 4 section

### Requirement: The release MUST be a minor bump with no breaking changes
On completion, `package.json` SHALL declare `0.6.0`, `.specboot.json` SHALL reflect `frameworkVersion: 0.6.0` (dogfooding), and `CHANGELOG.md` SHALL include a `## [0.6.0]` entry without a `### Breaking changes` section.

#### Scenario: Minor bump before merge
- **GIVEN** the framework at version 0.5.0
- **WHEN** the change completes and the maintainer bumps before merge (per the `version-bump` spec)
- **THEN** `package.json` and `.specboot.json` declare 0.6.0
- **AND** `CHANGELOG.md` contains the `## [0.6.0]` entry with no `### Breaking changes` section
