## Requirements
### Requirement: enrich-us output MUST include strategic evaluation metadata
The `enrich-us` skill SHALL output four strategic evaluation sections: Estimación (complexity and justification), Riesgo (risk level and reason), Dependencias (related tickets), and Alternativas descartadas (discarded alternatives).

#### Scenario: Enriched story includes strategic metadata
- **GIVEN** a story enriched via the `enrich-us` skill
- **WHEN** the output file is generated
- **THEN** it includes sections for Estimación, Riesgo, Dependencias, and Alternativas descartadas

### Requirement: Acceptance scenarios MUST include SC-NNN stable identifiers
All Gherkin acceptance scenarios generated by `enrich-us` and `plan-change` SHALL carry a unique `SC-{NNN}` prefix in their title header (e.g. `### SC-001: Scenario title`).

#### Scenario: Scenarios contain SC-NNN identifier
- **GIVEN** an OpenSpec change or enriched ticket artifact
- **WHEN** acceptance scenarios are rendered
- **THEN** every scenario header starts with `### SC-` followed by a three-digit integer and title

### Requirement: verify skill MUST track test coverage by SC-NNN pattern
The `verify` skill SHALL match test evidence against Gherkin scenarios using the `SC-{NNN}` pattern and map each scenario to PASS, FAIL, or UNTESTED status with an explicit evidence priority: a match on the test name or identifier (e.g. `[SC-001]` in the test title, `test_sc001_` in the function name) is strong evidence and may yield PASS or FAIL; a textual mention (comments or descriptions) is weak evidence, SHALL be flagged as such and SHALL never be counted as PASS; no reference yields UNTESTED. The verify report SHALL show the explicit `SC-NNN → test → status` traceability.

#### Scenario: Verify skill maps test evidence using SC-NNN
- **GIVEN** an active change with `scenarios.md` containing `SC-{NNN}` identifiers
- **WHEN** `verify` runs test verification
- **THEN** it matches test cases by `SC-{NNN}` pattern and includes the mapping in its summary

#### Scenario: Evidence priority in the scenario-to-test mapping
- **GIVEN** a scenario `SC-NNN` and tests referencing it in different ways
- **WHEN** verify maps the evidence
- **THEN** a name/identifier match is treated as strong evidence (PASS or FAIL)
- **AND** a textual mention is treated as weak evidence (flagged, never PASS)
- **AND** no reference yields UNTESTED

### Requirement: Tests generated during apply MUST carry SC-NNN in the test name
Tests generated by `/apply` SHALL include the scenario ID in the public test name: a `[SC-NNN]` prefix in the test title for JavaScript/TypeScript, and a `test_sc{NNN}_` prefix in the function identifier for Python. The convention SHALL be documented in `ai-specs/agents/build-agent.md` and referenced by the `backend-developer.md` and `frontend-developer.md` subagents. `docs/base-standards.md` is framework-injected and SHALL NOT be modified by this convention.

#### Scenario: Generated tests carry the SC-NNN prefix
- **GIVEN** an `/apply` task with a `Test Path` and an associated `SC-NNN` scenario
- **WHEN** the subagent generates the test (JS/TS or Python)
- **THEN** in JS/TS the test title carries the prefix: `test("[SC-001] ...")` / `it("[SC-001] ...")`
- **AND** in Python the identifier carries the prefix: `def test_sc001_...`
- **AND** the convention is documented in `ai-specs/agents/build-agent.md` and referenced by `backend-developer.md` and `frontend-developer.md`
